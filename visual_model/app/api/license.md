这段代码是基于 **FastAPI** 开发的一套完整的**授权验证API路由**，核心围绕授权码的验证、管理及配套辅助功能展开。其实现思路可从**整体架构设计**、**核心接口逻辑拆解**、**通用设计规范**三个维度清晰梳理，整体遵循“接口层-服务层”分离的设计模式，聚焦授权验证的安全性、灵活性和可运维性。

### 一、整体架构设计

1. **核心定位**
   该路由模块是授权验证功能的对外接口入口，所有与授权相关的客户端请求（如验证授权码、获取令牌、查询系统状态等）均通过此模块接收，再转发给 `license_service`服务层处理核心业务逻辑，路由本身仅负责请求校验、响应格式化和异常处理。
2. **依赖与基础配置**
   - **路由基础**：通过 `APIRouter`创建前缀为 `/license`的路由组，并用 `tags=["授权验证"]`归类，方便接口文档自动分组。
   - **数据模型**：依赖 `app.models.license`中定义的Pydantic模型（如 `LicenseVerifyRequest`、`LicenseVerifyResponse`等），实现请求参数校验和响应格式标准化。
   - **核心服务**：调用 `license_service`封装的授权相关业务逻辑，避免路由层包含复杂业务代码，降低耦合度。
   - **日志工具**：通过 `logger`记录关键操作和异常信息，便于问题排查。
3. **核心设计原则**
   - **分层解耦**：接口层仅处理HTTP请求/响应，业务逻辑全部下沉到服务层。
   - **场景覆盖**：同时支持在线/离线验证、授权码持久化等，适配不同网络和使用场景。
   - **异常分级**：区分客户端错误（400）和服务端错误（500），返回清晰的错误详情。

### 二、核心接口逻辑拆解

路由包含10个接口，可分为**核心授权验证接口**、**辅助状态查询接口**、**授权持久化接口**三类，每类接口均有明确的功能定位：

1. **核心授权验证接口**
   这类接口是模块核心，聚焦授权码的有效性验证和令牌生成，保障授权功能的核心可用性。| 接口                       | 请求方式 | 核心功能                             | 实现思路                                                                                                                                                                                                          |
   | -------------------------- | -------- | ------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
   | `/license/verify`        | POST     | 智能验证授权码（默认离线，在线备选） | 1.  校验请求参数：确保授权码和Token不为空；`<br>`2.  调用服务层智能验证方法，支持优先离线验证；`<br>`3.  验证成功则格式化过期时间、签发时间等数据返回；`<br>`4.  验证失败则返回具体原因，同时记录警告日志。 |
   | `/license/token`         | GET      | 获取当前时间对应的Token              | 1.  调用服务层 `get_current_token`生成令牌；`<br>`2.  成功则返回Token，失败则返回错误原因，适配Token强制校验场景。                                                                                            |
   | `/license/verify-online` | POST     | 纯在线授权验证                       | 1.  校验授权码非空；`<br>`2.  调用服务层在线验证方法（依赖外部独立生成端接口）；`<br>`3.  适用于需要强联网校验的场景，与智能验证形成功能互补。                                                                |
2. **辅助状态查询接口**
   这类接口不直接参与授权验证，核心作用是提供环境和服务状态，方便排查授权相关问题，提升运维效率。| 接口                        | 请求方式 | 核心功能         | 实现思路                                                                                                                                                                                                         |
   | --------------------------- | -------- | ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
   | `/license/system-info`    | GET      | 获取系统基础信息 | 调用服务层 `get_system_info`，返回系统硬件/软件相关信息，用于授权绑定（如MAC地址绑定）场景的问题排查。                                                                                                         |
   | `/license/network-status` | GET      | 查询网络连接状态 | 1.  调用服务层检查网络连通性；`<br>`2.  返回网络状态，并根据连通性推荐验证模式（离线/在线）；`<br>`3.  网络异常时也返回标准响应，避免客户端报错。                                                            |
   | `/license/health`         | GET      | 授权系统健康检查 | 1.  综合校验多维度状态：MAC地址获取、公钥可用性、外部生成端连接状态、网络状态；`<br>`2.  判断公钥来源（默认/远程），标记生成端连接状态；`<br>`3.  最终返回 `healthy`/`unhealthy`状态，方便监控系统对接。 |
   | `/license/storage-info`   | GET      | 获取授权存储详情 | 调用服务层 `get_storage_info`，返回授权存储目录、文件状态、记录条数等信息，用于排查持久化授权的存储问题。                                                                                                      |
3. **授权持久化接口**
   这类接口用于管理授权码的持久化存储，避免用户重复输入授权码，提升使用体验。| 接口                          | 请求方式 | 核心功能               | 实现思路                                                                                                                                                                                  |
   | ----------------------------- | -------- | ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
   | `/license/persistent/check` | GET      | 检查持久化授权状态     | 1.  调用服务层查询存储的授权码；`<br>`2.  若有效则格式化过期时间等信息返回；`<br>`3.  若无效，返回 `valid=false`但不抛出400错误，减少前端不必要的告警。                             |
   | `/license/persistent/save`  | POST     | 保存授权码到持久化存储 | 1.  校验授权码非空；`<br>`2.  调用基础验证方法校验授权码有效性（放宽Token校验，适配用户已成功验证后的保存场景）；`<br>`3.  验证通过后调用服务层保存，成功返回提示，失败返回具体原因。 |
   | `/license/persistent/clear` | POST     | 清除持久化授权         | 调用服务层删除存储的授权码，适用于用户更换授权码或注销授权的场景，同时记录操作日志便于追溯。                                                                                              |

### 三、通用设计规范

为保证接口的稳定性和可维护性，所有接口遵循统一的设计规范，这也是代码的核心实现亮点：

1. **严格的请求校验**
   对关键参数（如授权码、Token）做非空校验，若不符合要求直接返回 `400 Bad Request`，提前拦截无效请求，减少服务层压力。
2. **标准化的异常处理**
   每个接口均通过 `try-except`捕获三类异常：
   - 主动抛出的 `HTTPException`：直接抛出，返回预设的客户端/服务端错误。
   - 业务逻辑异常：记录错误日志（含堆栈信息），返回 `500 Internal Server Error`并附带具体原因。
   - 通用异常：兜底处理，确保接口不会因未捕获的异常崩溃。
3. **规范化的响应格式**
   所有接口通过 `response_model`指定响应模型，借助Pydantic强制响应数据结构统一。例如授权验证成功需返回 `valid`、`customer`等字段，失败需返回 `valid`和 `reason`，避免客户端因响应格式混乱报错。
4. **完备的日志记录**
   关键操作（如授权成功、保存持久化授权）记录 `info`级日志，异常情况记录 `error`级日志并附带堆栈信息，便于后续定位问题，提升系统可运维性。
5. **适配多场景需求**
   区分在线/离线验证、支持授权码持久化，同时提供健康检查、网络状态查询等辅助接口，既满足普通用户的授权需求，也适配运维人员的排查需求，兼顾易用性和可维护性。
